# A1_1의 2차 하락·3차 100%와 A2_1의 차이

2026-11-09(KST), [A2_1 이슈 #31](https://github.com/ntt65/A2_1/issues/31)의 읽기 전용 비교 기록이다. 사용자가 말한 “AI 심화 1-1도 두 번째에 떨어졌다가 세 번째에 100%였다”는 흐름을 A1_1의 평가 원문·Git 이력·README 변경으로 확인했다. A1_1에는 파일을 쓰거나 실험을 다시 실행하지 않았다. 이 문서는 A2_1에서만 추가한다.

## 확인된 결론

**사용자의 기억이 맞다. A1_1은 18/19 → 17/19 → 19/19였다.** 2차에서 새로 FAIL이 된 두 문항에 대해 이론·실측 수치·한계·구현 위치를 README 본문에서 직접 설명했고, 3차 평가는 바로 그 새 문장을 인용해 PASS로 바꿨다. 이는 상세한 결과와 설명을 읽기 쉬운 본문에 두는 대응을 뒷받침한다. 다만 평가 대상 SHA·실제 수집 파일 전체가 원문에 없으므로, README만이 유일한 원인이라고 증명한 것은 아니다.

**A1_1의 만점 후 추가한 JPEG 단계별 계측과 노트북 보완을 만점의 원인으로 설명하면 시점이 뒤집힌다.** 100% 평가 시각은 2026-11-07 23:50:40이며, 그 뒤의 2026-11-08 07:55 변경은 이미 통과한 평가의 권고를 자체 검증으로 보완한 작업이다. [평가 원문](https://github.com/ntt65/A1_1/blob/f2778a6d1f158b5743453ba89041400d51a05211/docs/naito_eval_result.md), [후속 구현](https://github.com/ntt65/A1_1/commit/0c48be26f3ffd936318f3abc5e195607e17258dc), [후속 검증 기록](https://github.com/ntt65/A1_1/commit/df6d8a3950d842382d84a0320d4408f3f015e7b6).

### #13: IQR을 쓴다는 설명에서 분포와 실측 비교로 확장

- `IQR=Q3−Q1`, 경계 `Q1−1.5·IQR`, `Q3+1.5·IQR`을 코드와 연결하고, 사분위수가 극단값의 크기에 평균·표준편차보다 덜 민감하다는 선택 이유를 설명했다.
- 같은 규칙을 적용해도 표준정규분포는 경계 밖이 약 0.70%, `exp(N(0,1))` 로그정규 예시는 약 7.76%임을 구분했다. 이 값은 이론 분포 계산값이며 실제 거래 통계와 섞지 않았다.
- 실제 동일 거래 8,084행의 하한 미만 0행·상한 초과 212행(2.62%), 왜도 +1.554, EDA 보정 전후 표본분산 `0.000222373 → 0.000184101`(−17.21%), 같은 중앙값 `0.022017`을 표로 보여 줬다.
- 긴 꼬리의 유효 고액 거래도 탐지될 수 있고 상품군 혼합·IQR=0에서 한계가 있다는 해석을 붙였다. RFM·월별 집계는 원금액 합계 `202.212746`을 보존한다고 명시했다.
- `NB_CLEAN` 코드 셀 `a32f822f`에 전후 표 계산·출력을 추가하고 README·Q&A의 설명과 맞췄다.

이것은 “이상치를 처리했다”는 주장에 **선택 이유 → 조건 → 실제 전후 숫자 → 한계**를 붙인 보완이다. 3차 #13은 새 README의 선택 이유 문장을 근거로 들었다. 이론 비율이나 실제 표의 모든 숫자를 평가기가 읽었다고까지 단정하지 않는다. [평가 전 README](https://github.com/ntt65/A1_1/blob/317774e0f0ac3689138b2f884e1ab85c851dd1ae/README.md), [평가 전 Q&A](https://github.com/ntt65/A1_1/blob/317774e0f0ac3689138b2f884e1ab85c851dd1ae/docs/a1_1_evaluation_qa.md).

### #17: 메모리 크기에서 관측 병목과 검증 가능한 설계로 확장

- 이미지 200장, 32×32 RGB float32, 배치 상한 32, 워밍업 1회 후 3회라는 실제 측정 조건을 썼다. 전체 중앙값 2.115초, `imread()`의 읽기+디코딩 중앙값 1.797초, 실행별 비중 중앙값 84.9%를 기록했다.
- 캐시 키에 상품 ID·파일 버전·피처 설정을 넣고, 캐시 미스만 제한된 워커가 읽기·디코딩·축소한 뒤 유한 대기열로 넘기며 상품 위치대로 결과를 병합하는 설계를 제시했다.
- 워커 1·2·4개를 같은 입력에서 비교할 때 처리량·최대 메모리·오류뿐 아니라 순서·상태·결측 위치·수치 일치를 확인하도록 했다. 이 워커 비교는 **향후 설계의 검증 절차**이며 실제 구현·측정 완료로 쓰지 않았다.
- 1024×1024 RGB 한 장의 float32 12 MiB·float64 24 MiB, 축소 버퍼 384 KiB 상한과 전체 프로세스 메모리를 구분했다. 동시 디코딩·대기 배열·stack 사본·임시 통계 배열도 메모리에 포함했다.
- 상품군·해상도별 고정 표본과 거래 청크 집계, 구매일 중복 제거까지 입력 규모와 결과 일관성의 조건을 설명했다.

## A2_1에 적용할 대응과 완료 기준

1. **계산 결과와 판단을 본문에서 끝까지 연결한다.** 각 기본 실험에 입력·수식·shape·반복 예산·실제 표·판정 기준·한계·재현 명령·원본 링크를 함께 적는다. A1의 효과적인 변화는 파일 이름을 더 나열한 것이 아니라 문항의 질문에 직접 답한 것이다.
2. **실제로 재실행한 결과에서 보고서를 만든다.** 기존 세 스크립트와 두 노트북을 별도 임시 출력에 실행하고 원본 JSON과 대조한 뒤 다섯 상세 Markdown과 README 본문을 생성한다. 기존 PNG·JSON·노트북·링크는 보존한다.
3. **Q&A는 설명을 검증할 수 있게 쓴다.** A1의 “핵심 설명 → SRC → 검증 결과 → 한계” 형식을 참조하되 A2 수식·수치·독립 검증으로 채운다. A1의 데이터·메모리 사례를 A2 요구에 맞지 않게 복사하지 않는다. [A1 Q&A](https://github.com/ntt65/A1_1/blob/820220be6eec6e3461095985063a80f7650a10e9/docs/a1_1_evaluation_qa.md), [A1 평가 준비 의견](https://github.com/ntt65/A1_1/blob/820220be6eec6e3461095985063a80f7650a10e9/docs/a1_1_eval_review.md).
4. **수학적으로 틀린 평가 문구는 구현 기준으로 삼지 않는다.** A2의 원형 GD에서 lr=.5는 한 번에 수렴하고 1은 진동, 1보다 크면 발산한다. 수렴 반경은 원문 .1을 유지하며 64×64에 rank100을 강제하지 않는다. Momentum이 항상 우월하다는 결과를 만들지 않는다. [결정 D09~D11](../DECISIONS.md).
5. **완료를 두 종류로 구분한다.** #31의 완료 근거는 실제 재실행·기존 산출물 보존·표의 수치 검증·링크·회귀·레지스트리·PR/CI 기록이다. 외부 평가의 완료 근거는 새로운 외부 보고서이며, 현재 40%를 자체 검사로 바꾸지 않는다.

현재 #31에서 실행 중인 검사의 결과는 이 비교 문서에 미리 적지 않는다. 최종 검증·게시 상태는 이슈 #31의 기록을 따른다.
